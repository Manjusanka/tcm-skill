# TCM Skill V2 改进说明与面试口径

## 0. 先把项目性质说准确

这次改进不是重新训练一个中医大模型，也不是发明新的向量检索算法，而是把原有 RAG/Agent 能力抽象成一套**框架无关、策略可执行、证据可校验、决策可回放**的 Skill 协议。

面试中建议使用下面的事实边界：

- 原有项目提供了中医知识问答、混合检索、图谱补充和工具调用的业务基础；
- V2 是我针对生产化风险完成的工程抽象和可运行原型；
- 仓库包含配置、Schema、确定性策略脚本和单元测试；
- TopK、置信度和 Token 数是初始工程参数，不冒充线上实测结论；
- 当前不能声称已经完成医院生产验证、医疗器械认证或大规模真实用户 A/B 测试。

## 1. 90 秒总体介绍

> 第一版 Skill 的主要问题是控制逻辑大多写在 SKILL.md 的自然语言里，虽然人能看懂，但运行时是否真正执行依赖具体 Agent 框架和大模型，换到 Spring AI、LangGraph 或自研框架后容易产生语义漂移。同时，第一版使用固定 TopK、文档级引用和生成后自检，存在资源分配僵化、引用漂白以及同一个模型自我确认错误的问题。
>
> 我把第二版拆成框架适配层和可移植内核。适配层只负责接入模型、向量库和工具；内核通过统一 JSON Schema、确定性策略引擎、能力图、自适应检索预算、上下文编译器和证据账本来约束行为。模型负责理解开放语义，权限、版本、工具副作用和引用合法性由代码决定。最终每个结论都能追到 evidence_id、知识发布版本和策略 reason_code，出了问题可以判断是意图、召回、工具、上下文还是生成阶段，而不是只看最终答案猜原因。

## 2. V1 问题与 V2 改进总表

| 编号 | V1 问题或漏洞 | 可能后果 | V2 改进 | 对应实现 |
|---|---|---|---|---|
| 1 | 入口依赖 Codex 的 `SKILL.md` 与 `agents/openai.yaml` | 换框架后规则丢失或含义变化 | 框架适配层与可移植内核分离 | `skill.yaml`、`schemas/`、`scripts/` |
| 2 | 路由与安全主要是自然语言 | 模型可能跳步、误解或绕过规则 | 策略即代码 + 带条件的能力图 | `policy_engine.py`、`capability-graph.yaml` |
| 3 | 所有问题使用固定 TopK | 简单问题浪费资源，复杂/高风险问题证据不足 | 自适应检索预算 | `adaptive_retrieval.py` |
| 4 | 工具选择与执行边界不够硬 | 错工具、错参数、重复写、越权调用 | Plan-Validate-Execute 两阶段网关 | `tools-and-agent.md`、决策 Schema |
| 5 | 引用只挂在答案或段落上 | 引用存在但不支持具体结论，即“引用漂白” | Claim-Evidence 证据账本 | `evidence-ledger.schema.json`、`evidence_guard.py` |
| 6 | 上下文主要靠限长和截断 | 重复片段挤占窗口、证据被截断、关键约束丢失 | 按边际主张覆盖率编译上下文 | `context_compiler.py` |
| 7 | 只写了 ACTIVE 版本过滤 | 历史查询、灰度发布、回滚场景定义不足 | 不可变 Release 快照 + 查询时间语义 | `safety-and-versioning.md` |
| 8 | 记忆依赖“已确认”描述 | 确认状态、过期、撤回和冲突可能无法执行 | 记忆生命周期与来源链 | `retrieval-and-context.md` |
| 9 | 生成后仍可能由同一个模型自检 | 生成和校验错误高度相关 | 独立确定性 Evidence Guard | `evidence_guard.py` |
| 10 | 评测指标多但缺少故障归因 | 分数下降时不知道该改哪一层 | 分阶段指标、reason_code 与决策回放 | `evaluation.md`、`skill.yaml` |

## 3. 改进一：框架无关内核

### 原问题

第一版虽然写着“不绑定框架”，但真正可被 Agent 加载的入口仍是 Codex 风格的 `SKILL.md`，UI 元数据也位于 `agents/openai.yaml`。如果直接迁移到 Spring AI 或 LangGraph，只能人工重新解释这些自然语言规则，不能保证执行语义一致。

### 为什么修改

业务能力不应该把生命周期绑定在某个 Agent SDK 上。框架会变化，模型也会变化，但权限、有效版本、工具副作用、答案证据这些业务不变量不能变化。

### 改动方案

V2 分为两层：

- 适配层：Codex、Spring AI、LangGraph、MCP Host 或自研服务负责模型调用、状态存储和工具传输；
- 可移植内核：`skill.yaml`、JSON Schema 和标准输入输出脚本定义一致的决策语义。

脚本都使用 stdin/stdout JSON，既可以作为 Python 库调用，也可以作为 Sidecar、HTTP 服务或被 Java/C++ 重写。重写时以 Schema 和契约测试为准，而不是以框架类名为准。

### 面试回答

> 我没有把 Skill 等同于某个框架的 Prompt 文件，而是把它定义成一个业务能力协议。框架只是 Adapter，真正需要稳定的是输入输出契约、策略、证据和评测。所以即使把编排从 LangGraph 换成 Spring AI，核心 decision JSON 和 evidence ledger 仍然一致。

### 继续追问：这和微服务有什么区别？

> 微服务强调部署和网络边界，Skill 协议强调一次智能任务内部的语义、策略、证据和工具边界。它可以部署成微服务，也可以嵌入单体应用，两者不是同一层概念。

## 4. 改进二：自然语言规则升级为策略即代码

### 原问题

“高风险要升级”“权限不足不能检索”写在 Prompt 中，并不等于运行时一定执行。模型可能因为长上下文忽略规则，也可能在工具循环中先取数、后发现无权限，形成数据泄漏。

### 为什么修改

开放语义适合模型，封闭规则适合代码。权限、急症短路、写操作确认、重试次数和版本状态都有确定答案，不应交给生成模型自由发挥。

### 改动方案

`policy_engine.py` 接收语义特征而不是直接解析自然语言，然后按固定优先级决策：

1. 权限失败直接 `refuse`；
2. 急症直接 `emergency/escalate`；
3. 高风险且缺关键事实时 `clarify`；
4. 写操作进入确认与幂等流程；
5. 其余请求在 retrieve、graph、memory、tool 和 hybrid 中选择。

能力图把节点、条件、终态和循环上限显式化。模型可以提议工具，但不能改变图上的权限门和终态规则。

### 面试回答

> 我的原则是“模型做语义，代码做裁决”。比如模型可以识别用户在问药物相互作用，但是否允许查某租户数据、能否执行写操作、超时后能否重试，是策略引擎决定。这样能把不可控的 Prompt 约束变成可单测的代码约束。

### 继续追问：语义特征识别错了怎么办？

> 保留原始 query、抽取特征、置信度和 reason_code。低置信度进入澄清；高风险关键词和权限检查还有规则兜底；评测时把“特征抽取错误”和“策略执行错误”分开统计。

## 5. 改进三：固定 TopK 改成自适应检索预算

### 原问题

第一版统一采用向量 Top40、关键词 Top30、融合 60、rerank Top8。这组数可以作为上限或基线，但不适合所有请求：简单定义题不需要这么多候选，而歧义、多跳或高风险问题可能仍然不够。

### 为什么修改

TopK 本质是质量、延迟和成本的资源分配问题。它应该受 query 难度、精确词需求、多跳关系、风险等级、证据缺口和系统负载共同影响。

### 改动方案

`adaptive_retrieval.py` 从基础预算开始：向量 24、关键词 16、融合 32、rerank 6。随后用透明规则增减：

- 歧义度达到 0.40：扩大向量、关键词和融合候选；
- 出现药名、剂量、编号等精确词需求：关键词额外增加 8；
- 多跳关系：图谱来源增加到 10；
- 高风险：向量和关键词各增加 8、rerank 增加 2，并要求至少两个独立来源；
- 普通低风险且负载达到 0.80：候选缩减为约 75%；
- 高风险在高负载下不做质量降级，而是限流或升级人工。

所有结果受最大值约束：向量不超过 48、关键词不超过 36、图谱不超过 12、融合不超过 64、rerank 不超过 10。

### 三个可直接讲的例子

1. 普通定义题：24/16/0 -> 融合 32 -> rerank 6；
2. 低风险高负载：约 18/12/0 -> 融合 24 -> rerank 6；
3. 高风险、多跳、精确词问题：最多 48/36/10 -> 融合 64 -> rerank 9~10。

### 面试回答

> 我没有说动态 TopK 一定提高效果，而是把它看作预算控制器。最终要在固定评测集上同时比较 Recall@K、nDCG、答案正确率、引用忠实度、P95 延迟和 Token 成本。如果动态策略没有带来端到端收益，就回退到固定基线。

### 继续追问：为什么不用强化学习直接学 TopK？

> 当前数据量和反馈质量不足以支撑稳定的在线策略学习，医疗场景也要求可解释和可回放，所以先用透明规则建立可靠基线。积累足够日志后，可以用 Contextual Bandit 做低风险流量实验，但高风险仍保留硬下限和人工门。

## 6. 改进四：工具调用采用 Plan-Validate-Execute

### 原问题

第一版虽然有白名单、Schema 和阈值，但“工具置信度 0.75”本身可能仍来自未校准的模型。只要模型同时完成选择、参数生成和执行，就容易把一次语义错误直接放大成外部副作用。

### 为什么修改

工具调用不是普通文本生成。尤其涉及真实数据和写操作时，需要把“想做什么”和“允许做什么”拆开。

### 改动方案

1. Plan：模型只输出候选工具、参数、目的、置信度和证据需求，结构遵循 `tool-plan.schema.json`；
2. Validate：网关检查工具白名单、租户、ACL、Schema、字段范围、副作用等级和幂等键；
3. Execute：只有验证通过才调用；
4. Normalize：限制字段、行数和 Token，脱敏并记录来源版本；
5. Observe：写入 trace，不把原始栈和秘密交给模型。

`tool_gateway.py` 已实现工具是否在策略允许集合、请求授权集合、租户是否一致、置信度是否过门以及写操作是否带确认和幂等键的校验。

写操作不提供默认自动执行能力，必须明确授权、再次确认目标并携带幂等键。401/403、参数错误和非幂等写不自动重试。

### 面试回答

> 我把模型输出当作“执行计划”，不是命令。真正执行前要经过确定性网关。这样即使模型选错工具，错误也会停在 Validate 阶段，不会直接影响外部系统。

## 7. 改进五：从文档引用升级为 Claim-Evidence 证据账本

### 原问题

答案末尾有来源，不代表每个结论被来源支持。模型可能引用了相关文档，却说出文档中没有的剂量或禁忌，这就是引用漂白。

### 为什么修改

RAG 的关键不是“找到了文档”，而是“具体主张能否被具体证据支持”。需要把答案拆成可验证的 claim。

### 改动方案

V2 要求每条 claim 包含：

- `claim_id`：稳定标识；
- `kind`：事实、剂量、禁忌、相互作用、推断、不确定性或安全建议；
- `evidence_ids`：支持该主张的证据；
- 证据账本记录 release、版本、授权、权威性、审核状态和内容哈希。

`evidence_guard.py` 独立检查未知引用、无证据事实、越权证据、旧版本证据以及高风险主张是否使用权威来源。

### 面试回答

> 我不是只校验 citation 是否存在，而是校验 claim 到 evidence 的边。这样能区分“引用格式正确”和“引用真的支持结论”。证据账本还保存发布版本和哈希，因此同一个答案可以复现当时到底看到了什么。

### 继续追问：代码能判断语义蕴含吗？

> 当前确定性 Guard 只能验证身份、权限、版本和引用覆盖，不能完整判断自然语言蕴含。语义蕴含需要单独的 NLI 或 Judge Adapter，并且要做人工标注校准。这个限制我会明确说明，不会把“有 evidence_id”当作语义正确。

## 8. 改进六：上下文截断升级为上下文编译

### 原问题

按分数取 TopN 再截断，容易选出大量表达同一事实的重复片段；截断还可能切掉表格单位、否定词或引用边界。

### 为什么修改

有限窗口下应该最大化“新增信息”，而不是最大化相似度之和。上下文里的证据也应保持原子性，不能把一个表格行或完整禁忌拆成半段。

### 改动方案

`context_compiler.py` 使用带权边际覆盖：

`utility = (新增主张覆盖权重 + 0.15 × 质量分) / token_cost`

先放必须证据，再反复选择单位 Token 带来最大新增主张覆盖的证据。证据整体放入或整体不放；若必须证据超过预算，返回 `insufficient_budget_for_mandatory_evidence`，而不是偷偷截断。

### 面试回答

> Rerank 解决“相关不相关”，Context Compiler 解决“在固定窗口里如何组合证据”。两个高相关片段可能是重复的，所以我增加边际覆盖率，优先选择能覆盖新 claim 的证据。

### 继续追问：这是背包问题，贪心一定最优吗？

> 不保证全局最优。选择贪心是因为在线复杂度低、决策可解释。候选规模较小时可以离线用 0/1 背包或整数规划做上界对照，验证贪心损失是否可接受。

## 9. 改进七：文档版本从状态字段升级为 Release 快照

### 原问题

第一版已经提出 `ACTIVE` 过滤，但单个文档状态不能完整表达一批索引的原子发布。如果 100 个文档只更新了 70 个就开始提供检索，会形成混合版本知识库。

### 为什么修改

线上查询需要看到一个一致快照，而不是多个文档各自最新但彼此不一致的集合。

### 改动方案

- 每次构建生成不可变 `release_id`；
- 完成解析、数量、Checksum、回归检索和安全评测后，从 STAGING 原子切换 active release 指针；
- 查询默认固定在一个 release；
- 历史问题显式携带 `as_of_time`，不能通过降低新鲜度权重偷偷混入旧文档；
- 回滚只切换指针，不在线删除索引；
- 证据账本记录回答时使用的 release 和内容哈希。

### 面试回答

> 我把版本管理的粒度从 document 提升到了 release snapshot。这样一个请求里的所有 chunk 来自同一知识快照，避免半更新状态。旧版本用于审计和回滚，不参与默认召回竞争。

## 10. 改进八：记忆从相似度召回升级为生命周期数据

### 原问题

仅仅写“只召回已确认记忆”还不够。如果没有来源、确认时间、目的、过期时间和撤回状态，系统仍可能把旧过敏信息、模型推断或其他会话数据放进上下文。

### 为什么修改

记忆不是普通向量文档，它与用户身份、授权目的、时效和隐私直接相关。

### 改动方案

每条长期记忆至少包含 user/tenant、`source_turn_id`、confirmation、purpose、sensitivity、effective/expiry、supersedes 和 deletion 状态。召回顺序是先权限和生命周期硬过滤，再做任务相关性排序。高风险冲突不按相似度自动选胜者，而是澄清。

### 面试回答

> 我把 Memory 当作有生命周期的用户数据，而不是另一个向量库。向量相似度只能回答“像不像”，不能回答“能不能用、是否还有效”。

## 11. 改进九：生成与校验解耦

### 原问题

让同一个模型生成后再问它“你有没有幻觉”，容易出现相关性错误：生成阶段漏掉的风险，校验阶段也可能继续漏掉。

### 为什么修改

不同类型的错误应该交给不同机制：权限、版本、未知引用适合确定性代码；语义蕴含适合独立 Judge；高风险最终仍需人工。

### 改动方案

Evidence Guard 不访问生成模型内部思维，只检查结构化 claim、citation 和 ledger。可修复的格式问题最多返修一次；越权、旧版本、无证据高风险主张直接阻断或升级，避免无限反思循环。

### 面试回答

> 我没有追求一个万能 Judge，而是做分层校验。确定性错误由代码零容忍，语义错误由独立模型或规则评估，高风险由人工兜底。这样比同一个 LLM 自问自答更可靠。

## 12. 改进十：从最终分数升级为故障归因与回放

### 原问题

第一版列了 Recall@K、正确率和延迟等指标，但如果只看最终答案错了，无法判断是意图识别、版本过滤、召回、rerank、上下文选择、工具还是生成出错。

### 为什么修改

没有阶段归因，优化容易“头痛医脚”。例如召回本来正确，却盲目增大 TopK，反而让上下文噪声更高。

### 改动方案

每次请求记录：

- skill、policy、prompt、model 和 knowledge release 版本；
- 语义特征、路由 confidence 和 reason_code；
- 各路候选、去重、版本折叠、rerank 和最终证据 ID；
- 工具计划、验证结果、标准化结果和耗时；
- 上下文选择及未选原因；
- claim-evidence 边和 Guard 违规码；
- P50/P95/P99、Token 和工具成本。

离线回放固定模型和固定 release，只替换一个组件做对照，从而定位首个故障阶段。

### 面试回答

> 我的可观测性不是只打 latency 日志，而是保存可回放的决策数据。这样同一条 query 可以复现当时的策略、知识版本和证据组合，才能做真正的根因分析。

## 13. 原方案仍然存在的限制与后续方向

这些点要主动承认，反而更能体现工程判断：

1. 自适应预算目前是透明规则，不是从大规模流量学习出的最优策略；
2. Evidence Guard 还不能替代语义蕴含模型和人工医学审核；
3. 仓库提供逻辑工具协议，不包含真实医院 HIS、药物数据库或生产凭据；
4. 能力图是声明式状态机，具体并行、超时和持久化由 Adapter 实现；
5. 初始阈值必须通过真实语料校准，不能直接承诺 Recall 或 P99；
6. 医疗合规、审计留存和数据脱敏规则仍需按实际部署地区与机构制度补齐。

后续优先级建议：先接真实评测集和 Trace 回放，再做 NLI/Judge 校准，最后才考虑 Contextual Bandit 或自动策略学习。

## 14. 面试官连续拷打示例

### Q1：你这个 Skill 的创新到底在哪里？

> 不是某一个算法创新，而是控制面创新：把 Agent 中依赖 Prompt 的权限、路由、预算、版本和证据校验抽成框架无关、可执行、可测试的协议。最核心的三个点是策略即代码、自适应检索预算和 Claim-Evidence 账本。

### Q2：为什么这不只是配置文件堆砌？

> 因为配置后面有执行器和失败语义。`policy_engine.py` 真正输出路由，`context_compiler.py` 真正决定哪些证据进入窗口，`evidence_guard.py` 真正阻断越权或旧版本引用，并且都有单元测试。配置只是可版本化的控制面。

### Q3：怎么证明改进有效？

> 先建立 V1 固定 TopK 和 Prompt-only Guard 基线，再在同一冻结评测集上比较。检索看 Recall@K/nDCG，答案看正确率和 claim-level faithfulness，安全看关键违规数，工程看 P95/P99、Token 和工具成本。高风险、越权和伪造引用是硬门，不能被平均分掩盖。

### Q4：动态 TopK 会不会让延迟不稳定？

> 会，所以它必须有最大预算、超时和服务负载输入。普通请求可以负载降级，高风险请求不降低证据质量，而是限流、返回部分结果或升级人工。动态不等于无上限。

### Q5：为什么图谱要在 rerank 前？

> 图谱负责补充多跳候选并回源到 source chunk，它和向量、关键词候选一起去重、版本过滤和融合后再 rerank。如果 rerank 后才补图谱，新增证据没有经过与 query 的统一相关性判断，也容易超出上下文预算。

### Q6：模型完全不参与策略了吗？

> 不是。模型仍负责意图、实体、歧义和工具参数草案等开放语义任务，但输出的是受 Schema 约束的特征或计划。最终权限和副作用裁决由确定性策略完成。

### Q7：如果 Guard 拒绝了正确答案怎么办？

> 统计 Guard 的误拒率，并保留原因码。格式或漏声明 citation 可以自动返修一次；高风险证据不足不能为了通过率放宽。阈值调整必须在风险分层评测集上完成。

### Q8：这个项目你能现场演示什么？

> 可以用 JSON 输入分别演示普通问题、高风险相互作用、权限失败和高负载场景，展示不同 route、TopK 和 reason_code；再构造旧版本或越权 evidence，演示 Guard 直接阻断；最后跑全部测试证明这些边界可回归。
